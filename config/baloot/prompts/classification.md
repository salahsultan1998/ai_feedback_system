每条反馈独立完成以下判断，并忠实翻译全文。辱骂排除规则优先于有效性、模块和建议价值：

零、先检查是否含实际辱骂内容
1. 原文只要包含实际辱骂、粗口、人身攻击、恶意诅咒或侮辱性表达，整条排除。针对客服、其他玩家、团队或游戏的辱骂均适用；识别阿语口语、拼写变体及用空格、符号拆开的辱骂，也检查中文、英文等内容。
2. 即使同时包含明确故障、充值问题、合理诉求或有价值的产品建议，也必须整条返回 is_valid=false、exclusion_reason="含辱骂内容"、label=""、theme=""、subtheme=""。不能只删掉脏话后保留其余内容，也不能归入其他模块。
3. 实际辱骂即使出现在引用、转述中也排除。仅说“我被骂了”“举报有人骂人”但未写出实际辱骂表述，不等于正文含辱骂；普通负面评价、发牌不公平的投诉、宗教誓言本身也不自动算辱骂。
4. 排除项仍返回忠实翻译，供后台记录处理状态；后台会将整条排除出报告、统计和所有 Excel 工作表。

一、是否可以确定有效的反馈对象、诉求或交流意图（is_valid）
1. 内容可以理解、对象或诉求明确时，is_valid=true。文字短不等于无效，例如“金币丢了”“无法充值”应保留；明确的问候感谢、游戏链接咨询也可以保留。
2. 只有乱码、无法理解的内容，返回 is_valid=false、exclusion_reason="内容无法理解"。
3. 只说“恢复成以前那样”“这样不好”等，却无法确定指的是什么或有什么实际诉求，返回 is_valid=false、exclusion_reason="缺少明确反馈对象或诉求"。不从相邻反馈猜测对象。
4. 新功能建议即使不属于已有模块，也应保留为“其他”；缺少订单、截图、原因等细节不等于对象不明确。不要因为无法核实玩家说法而排除。
5. 无效反馈仍提供如实的中文翻译或无法理解的说明，但 label、theme、subtheme 必须全部为 ""。有效反馈的 exclusion_reason 必须为 ""。

二、三层分类（label、theme、subtheme）
1. 每条有效反馈只选择一个最主要的 I 类别：账号问题、游戏卡顿、玩法相关、充值、作弊、其他。正文优先，客服原标签可能不准确，不能照搬。
2. label 必须逐字匹配 labels 的键；theme 必须匹配该 I 类别的 themes 中一个 name；subtheme 必须匹配选中 theme 的 children 中一个 name。禁止跨父级选择。没有合适的 II 类别时 theme、subtheme 都为 ""；没有对应第三层或无法确定具体第三层时 subtheme=""。已明确具体活动或场景时选择完整路径，不只停留在上级。
3. 三层必须分别返回，例如 label="玩法相关"、theme="活动"、subtheme="许愿树"。后台导出时才显示为“活动（许愿树）”，不要将括号拼进 theme。“建议”不是任何层级的类别。
4. 找回、登录、绑定及跨设备登录方式问题归“账号问题”。卡顿、延迟、掉线、游戏中断或闪退归“游戏卡顿”；不能把中断一律译成闪退，不能自行断定是网络差。
5. 充值和付费主诉求优先归“充值”。明确 VIP 无法充值用 II 类别“VIP无法充值”；付费后未到账及业务约定的扣款金额争议用“充值未到账”；兑换卡问题用“兑换充值卡”；其他无法充值、咨询充值方式等用“其他充值问题”。标签名称不能使译文增加“未到账”“重复扣款”等原文未说明的事实，不再使用“充值咨询”。
6. 加入、退出或切换俱乐部异常、俱乐部贡献等，归“玩法相关 → 俱乐部”，不能因源标签写网络卡顿而改归网络问题。战绩记录相关诉求统一归“其他 → 个人信息页面”；相册入口、上传、新增或恢复诉求归“其他 → 相册功能”。这两类没有第三层。
7. 对局规则举报由玩家发起、系统判定。该机制及其滥用争议归“玩法相关”，明确场次时选择相应 II 类别，例如“翻倍场”；不能仅因“举报”就认定聊天举报、作弊或游戏限制。保留谁发起举报、谁将得零分、谁的得分受影响，未提及裁定结果时不补写已处罚。
8. 明确作弊、通牌、举报 AI、单纯队友故意坑人按现有 II 类别归“作弊”；明确要求改善匹配时以“玩法相关”为主。发牌不公平、输多赢少归“玩法相关 → 发牌&公平 → 对应 III 类别”。
9. 玩法准入、点赞赠送等运营限制归“玩法相关 → 游戏限制 → 对应 III 类别”；已明确限制但不属于所列具体限制时用“其他玩法限制”。段位、赛季问题归“玩法相关 → 段位与赛季”，赛季结算或奖励诉求用 III 类别“赛季结算&赛季奖励”。
10. 活动咨询和非付费活动问题归“玩法相关 → 活动 → 对应活动”，例如询问沙漠寻宝结束时间。金币异常丢失归“其他 → 金币丢失”。普通可理解的不满归“其他 → 抱怨”；问候感谢、游戏链接、普通规则咨询按“其他”的对应 II 类别分类。
11. 封禁、禁言及封禁申诉如果仍出现，统一归“其他 → 封禁”；不再使用独立“举报”模块。“我被骂了”但没有写出实际辱骂内容时可保留，在“其他”下按实际诉求归类，不凭被辱骂本身推断已经封禁。含实际辱骂的整条反馈始终优先排除。
12. 新游戏建议或其他对象明确但不属于现有 II 类别的内容，可归 I 类别“其他”，theme、subtheme 留空，不能新增分类。

三、原标签与建议候选（由后台处理）
1. 不判断也不返回 is_suggestion。后台会仅将原标签明确标记为“建议”的有效反馈作为建议候选；不要自行把未标记为建议的反馈提升为候选。
2. 当前只负责全文翻译、辱骂及语义有效性检查、模块分类。原标签为“建议”不改变其所属模块；是否值得进入最终建议摘要，由后续提炼阶段筛选。

四、翻译保真
1. translation_zh 使用简体中文，忠实保留全文的主次诉求、主体、条件、否定、金额、数字、账号及玩家的怀疑程度。不得把玩家主张写成已证实事实，不添加核查结果或补偿结论。
2. 能确定的游戏名称使用表内中文。结合上下文识别口语和拼写变体；未填写或只有点号的词条没有词义，不凭模糊词猜测更具体的玩法。
3. كبوت 固定译为“打光头”，表示使对方得零分。区分打光头和被打光头、即将发生和已经发生。project 使用业务允许的英文称呼，保留 project 400 的数字，不补单位。
4. 不理解的片段如实说明，不编造含义；建议和问题不因翻译压缩而被删除。
